# Store Shipping Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the experimental fixed-type shipping model with flexible per-Store shipping methods, optional logos, unified Store Management CRUD/reorder controls, and server-authoritative checkout/order snapshots.

**Architecture:** Shipping methods remain tenant-schema business data. Unified Store Management resolves Store -> trusted tenant -> tenant DB with `requireStoreManagementDb(...)`; checkout continues to load active methods from the trusted tenant DB and recomputes price/address requirements server-side. Existing media infrastructure is extended with a tenant-scoped `shipping` media kind; only the picker/preview is client-side.

**Tech Stack:** Next.js 15 App Router, TypeScript, PostgreSQL 17, Drizzle ORM, Zod, node-postgres, React 19, next-intl, react-dropzone, existing ShopNest media helpers.

**Spec:** `docs/superpowers/specs/2026-10-04-store-shipping-management-design.md`

## Global Constraints

- Follow `docs/DEVELOPMENT_GUIDELINES.md` and `docs/ADMIN_UI_STANDARDS.md`.
- Use feature branch `feature/store-shipping-management`; never work directly on `master`.
- All user-controlled mutation payloads must be parsed as complete objects with server-side Zod before business logic or persistence.
- Prefer Drizzle for DB access; use raw SQL only where an existing invariant requires it, such as advisory locks.
- Tenant/store/schema authority must be server-resolved; browser-supplied Store IDs are lookup inputs only.
- Cross-Store and cross-tenant requests fail closed.
- Checkout price, active state, address requirement, and order totals are server-authoritative.
- Normal management controls use the shared 44px UI standard and same-page mutation behavior where the destination does not change.
- Do not reset databases, drop unrelated tenant data, or delete Docker volumes.
- Do not merge any PR without explicit user approval.

## Review Focus

- Decimal ILS input such as `15.50` must normalize exactly to integer minor units and reject excess precision rather than round silently.
- A logo replacement/removal request must be unable to delete a file outside the current Store tenant or outside the `shipping` media kind.
- A stale checkout that submits a method made inactive after page render must fail closed when the order is created.
- Reorder requests containing duplicates, omitted methods, or cross-tenant IDs must fail without partially changing sort order.
- Existing order display must use the order snapshot after the live shipping method name/price/logo changes or the method is removed.

4. after successful DB update, delete the previous logo through the same trusted tenant parser

For logo removal, read the current row from the current tenant DB first; never delete a browser-submitted path.
