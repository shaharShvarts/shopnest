## 1. Purpose

Add a trusted control-plane custom-domain model and resolve eligible HTTP Host values to the same trusted Tenant identity already used by path-based routing.

This is GitHub PR #45 because the earlier roadmap numbering shifted after the copy-only PR #42.

This PR owns:
- public.store_domains control-plane model
- exact hostname normalization and validation
- trusted active-domain -> active-Tenant lookup
- bounded positive/negative cache
- middleware Host routing
- clean custom-domain storefront/admin URLs without exposing the Store slug
- path-based ShopNest routing compatibility
- fail-closed behavior for unknown/inactive custom hosts

This PR does not call Cloudflare or mutate public DNS.

## 2. Trust flow

Trusted custom-domain routing:

request Host
-> normalize exact hostname
-> public.store_domains exact lookup
-> require domain status=active
-> tenant_id
-> public.tenants
-> require Tenant status=active
-> validate canonical Tenant slug/schema
-> trusted Tenant context
-> schema-scoped DB access

Never:

Host
-> derive slug
-> derive schema
-> SET search_path

The browser-supplied Host value is lookup input only. It never becomes a schema identifier or authorization decision by itself.

## 3. Domain entity

Add public.store_domains.

Initial fields:
- id
- tenant_id
- hostname
- type
- status
- verification_token
- verified_at nullable
- is_primary
- created_at
- updated_at

Initial type:
- custom

Lifecycle statuses:
- pending_verification
- verified
- active
- failed
- removed

Only active rows are routable.

verified and active require verified_at.

hostname is canonical lowercase ASCII/punycode with no trailing dot or port and is globally unique.

verification_token is opaque, server-generated by future management/automation flows. This PR stores the field but does not implement DNS verification automation.

At most one row per Tenant may have is_primary=true.

## 4. Hostname normalization

Custom hostname validation is server-side and exact.

Rules:
- lowercase canonical comparison
- optional incoming port is stripped before lookup
- one trailing DNS dot is normalized away
- no scheme, path, userinfo, wildcard, whitespace, slash, backslash, or control characters
- valid DNS labels only
- label length <=63
- full hostname length <=253
- at least two labels
- localhost and IP literals are not custom domains

Internationalized domains are stored/resolved in their ASCII punycode representation.

## 5. Platform hosts

Path-based routing remains authoritative on ShopNest platform hosts.

Initial platform-host classification:
- shopnest.co.il
- any subdomain of shopnest.co.il, including staging.shopnest.co.il
- localhost
- IP literals used for local/server acceptance

On platform hosts:
- existing /<tenant>/... behavior remains unchanged
- global marketing/merchant/admin routes remain global

On non-platform hosts:
- the Host must resolve through public.store_domains
- unknown/inactive domain -> 404
- registry/database lookup error -> 503

This prevents an arbitrary external Host header from silently falling back to the ShopNest marketing site or selecting a Tenant by path.

## 6. Custom-domain URL behavior

A custom domain exposes clean Tenant URLs.

Examples:

www.pandapop.co.il/
www.pandapop.co.il/categories
www.pandapop.co.il/admin
www.pandapop.co.il/api/cart/add
www.pandapop.co.il/media/products/x.jpg

Internally, Tenant page requests are rewritten to the existing physical /[tenant]/... route while the browser URL remains clean.

Tenant handlers already physically live at /api/... and /media/..., so custom-domain handler requests keep their clean path while trusted Tenant headers are injected.

The custom Host takes precedence over the first path segment. A path that happens to look like another Store slug cannot switch Tenant context.

## 7. Navigation context

The current trusted Tenant identity keeps its canonical basePath /<slug>.

For browser navigation:
- platform path mode uses /<slug>
- custom host mode uses an empty public base path

Middleware writes a trusted route-mode header and overwrites/removes any client-supplied value.

TenantProvider may accept:
- /<slug> for path mode
- empty base path for trusted host mode

prefixTenantPath continues to validate local paths. Empty-base host mode returns the validated local path without a Store slug prefix.

This affects navigation only. Tenant authorization and database selection still use the trusted server Tenant identity.

## 8. Middleware precedence

1. parse and validate Host
2. if platform host, run existing path-based Tenant resolution
3. otherwise resolve exact custom domain
4. inject trusted Tenant slug/schema/route-mode/internal-path headers
5. custom-domain page route -> rewrite to /<tenant-slug><path>
6. custom-domain /api and /media handlers -> keep physical handler path with trusted headers
7. unknown/inactive custom host -> 404
8. resolver failure -> 503

Global OAuth/payment callbacks remain canonical platform-host endpoints and are not accepted as Tenant custom-domain callbacks in this PR.

## 9. Cache

Use a short process-local cache equivalent to the Tenant registry cache.

Default TTL: 5 seconds.

Cache:
- positive active domain resolution
- negative not-found/inactive resolution

Do not cache resolver exceptions as not-found.

Future domain status mutations must clear the affected hostname cache after commit.

## 10. Migration

Add one journaled control-plane migration for public.store_domains.

No Tenant schema migration is required.

The migration must be:
- additive
- safe on existing DEV/STAGING data
- idempotency/hash compatible with the existing control-plane provisioner
- non-destructive

## 11. Security invariants

- Host never becomes a PostgreSQL schema name
- domain lookup must join through trusted public.tenants
- domain and Tenant must both be active to route
- exact hostname uniqueness is enforced by DB constraint
- spoofed x-shopnest-* headers are overwritten
- unknown external hosts fail closed
- inactive/removed domains fail closed
- suspended/disabled Tenants fail closed even if domain is active
- lookup/database errors return 503, not another Tenant or platform fallback
- no wildcard domain routing in this PR
- no DNS/Cloudflare trust assumptions
- no browser-supplied tenant_id/schema/status

- inactive domain fails closed

- unsafe Tenant schema fails closed

- resolver exceptions not cached
- platform Host preserves existing path routing
- unknown external Host -> 404
- resolver DB error -> 503
- custom-domain root/page/admin routing injects trusted headers and rewrites to /<slug>/...
- custom-domain /api and /media keep clean handler paths
- path containing another Store slug cannot switch custom-host Tenant
- spoofed internal headers are overwritten
- custom-domain navigation uses clean paths
- existing route/tenant-registry tests remain green
- production build passes

DEV acceptance:
- run control-plane migration
- existing registry-test remains routable by path
- create one temporary active store_domains row pointing to registry-test
- curl custom Host to root/page -> 200 or expected app response with trusted Tenant context
- unknown Host -> 404
- mark domain inactive/removed -> 404 after cache TTL

STAGING repeats the same non-destructive acceptance before READY TO MERGE.

## 13. Out of scope

- Cloudflare API
- DNS record creation/deletion
- nameserver changes
- certificate issuance automation
- automatic domain ownership verification
- merchant self-service domain UI
- custom-domain purchase
- wildcard custom domains
- redirect/canonical-primary-domain policy
- changing Store activation/readiness
- changing customer/admin identity models
